# Architecture

Te Pinta 3.0 is a modular Laravel 13 monolith with an Inertia 3 + React 19 + TypeScript frontend and PostgreSQL 18 as the only supported database. Laravel owns authentication, authorization, validation, prices, totals and state transitions; PostgreSQL is the final integrity boundary (constraints, triggers, exclusion constraints); React composes workflows and renders backend results.

## Code layout

```text
app/
  Core/       application-wide contracts, value data, tenancy, safety guards (no business module dependencies)
  Shared/     narrowly named reusable infrastructure (request logging)
  Modules/    one directory per business capability: Actions, Data, Enums, Events, Http, Listeners,
              Models, Policies, Pricing, Queries, Support, routes.php — only the folders it needs
resources/js/
  pages/               thin Inertia route entry points (admin, auth, public)
  layouts/             public, admin, settings and auth shells
  features/<feature>/  feature-owned components, hooks and types
  components/ui/       shadcn/ui primitives
  components/shared/   Te Pinta reusable compositions (sidebar, page shell, empty state)
  lib/, hooks/         focused helpers
  actions/, routes/, wayfinder/  generated by Laravel Wayfinder
```

Controllers coordinate HTTP. Form Requests authorize and validate. Actions execute one use case inside a transaction. Queries build read models. Models persist relationships. Do not add generic repositories, base services or empty folders.

## Modules

| Module | Responsibility |
| --- | --- |
| `Core` | `ProductPriceProvider` contract + `SellableProductPrice`, `PublicIdentifier`, `RestaurantContext` (tenancy), `TestingDatabaseGuard`, `Branding` (validated restaurant accent palette) |
| `Shared` | `AssignRequestId` (request ID in log context) and `LogAdminRequest` (`admin.request.completed`) middleware |
| `Identity` | Users, per-restaurant memberships (`restaurant_user`), code-defined roles and permissions, `restaurant.member` middleware, user management (`/admin/users`), `admin:create` console command |
| `Products` | Categories, products, tags, availability, pricing family (`empanada`/`unit`), cooked base prices, raw-price discounts, public catalog and product detail |
| `Customers` | Customer profiles, phone normalization, search, history, soft delete and restore |
| `Orders` | Order creation (admin, public checkout, POS), editing, snapshots, revisions, status and payment transitions, pricing engine, table service (sessions, immutable rounds, bill, charge), WhatsApp link |
| `Settings` | Admin write surface for restaurant branding, ordering settings, raw-price discounts and add-ons (`/admin/settings/general`) |
| `Inventory` | Items, units, categories, purchase presentations, stock movements, cost layers, valuation, recipes, production, adjustments, order consumption, current product costing |
| `Management` | Wallets, immutable ledger, outflows, transfers, distributions, order payments, rich purchases, attachments, financial summary and audit (UI label: **Gestión**) |
| `Dashboard` | Read-only operational dashboard over order snapshots (`/admin/dashboard`) |
| `Marketing` | Featured-product scheduling, public-safe view model, dashboard summary |
| `Instagram` | Story assets, schedules, publication queue, n8n automation API, signed media |
| `PublicSite` | Public routes (`/`, `/menu`, `/cart`, checkout endpoints) delegating to Products and Orders |
| `Restaurant` | Physical floor configuration: dining areas and tables (`/admin/restaurant/floor`) |
| `Analytics` | Unused `AnalyticsReader` interface only; no route or page until metrics are defined |

`Inventory\Contracts\InventoryAvailability` and `Dashboard\Contracts\PublicPromotionFeed` are declared but have no implementation or caller.

## Request flows

```text
Admin browser
  -> web middleware (AssignRequestId, Inertia) -> auth + verified + restaurant.member + admin.request.log
  -> can:<permission> (route) -> module controller -> Form Request (authorize + validate) -> policy
  -> Action (DB transaction, row locks) -> PostgreSQL constraints/triggers
  -> Inertia page, redirect or JSON preview

Public checkout (no session user)
  -> /checkout/price-preview (throttle 20/min) or /checkout/orders (throttle 5/min)
  -> slug resolution to internal IDs -> OrderPricingEngine -> CreateOrder
  -> atomic customer match/create + order snapshots -> summary + wa.me link

n8n automation
  -> /api/automation/instagram/stories/* (throttle 30/min, then bearer token) -> Instagram actions
```

Every admin route is registered inside one group in `routes/web.php` with `auth`, `verified`, `restaurant.member` and `admin.request.log` and the `/admin` prefix, and declares its own `can:<permission>` middleware in its module `routes.php`.

## Cross-module integration

Synchronous application events, registered in `app/Providers/AppServiceProvider.php`, run inside the emitting transaction; a listener failure rolls back the triggering change.

| Event (Orders) | Listener | Effect |
| --- | --- | --- |
| `OrderPaymentConfirmed(orderId, amount, confirmedOn, adminId)` | `Management\Listeners\RecordConfirmedOrderPayment` | One `ManagementOrderPayment` + ledger entry; automatic distribution when an active rule exists |
| `OrderDelivered(orderId, businessDate, adminId)` | `Inventory\Listeners\RecordDeliveredOrderConsumption` | Physical consumption and historical COGS |
| `OrderDeliveryCancelled(orderId, businessDate, adminId)` | `Inventory\Listeners\ReverseCancelledOrderConsumption` | Exact reversal of that consumption |

Orders reads product prices only through `Core\Contracts\ProductPriceProvider` (bound to `Products\Pricing\DatabaseProductPriceProvider`).

## Dependency rules

1. Core never depends on a business module.
2. A module never calls another module's controller or Form Request.
3. Cross-module writes go through events or a narrow contract, not through another module's tables.
4. Pages compose feature or shared UI; shared UI never imports feature code.
5. PublicSite and Dashboard consume Marketing's read models instead of reimplementing its temporal or eligibility rules.

### Known violations (verified in code)

| Violation | Evidence |
| --- | --- |
| Orders imports Products models directly | `Orders/Models/OrderItem.php`, `Orders/Models/OrderItemComposition.php`, `Orders/Actions/BuildAdminOrderFormOptions.php`, `Orders/Actions/BuildOrderDashboardData.php` |
| Customers ↔ Orders cycle | `Customers/Models/Customer.php` and `Customers/Http/Controllers/CustomerManagementController.php` import Orders; `Orders/Models/Order.php`, `Orders/Actions/ResolveOrderCustomer.php` import Customers |
| Products ↔ Orders cycle | `Products/Pricing/DatabaseProductPriceProvider.php`, `Products/Http/Controllers/ProductManagementController.php` and `Products/Actions/RecalculateEmpanadaUnitPrices.php` read `Orders\Models\OrderSetting` |
| Settings writes Orders and Products tables | `Settings/Actions/UpdateOrderingSettings.php` writes `OrderSetting`, `OrderAddon`, `RawPriceDiscount` |
| Management depends heavily on Inventory | Rich purchases (`Management/Actions/CreatePurchase.php`, `ReversePurchase.php`, `Models/PurchaseLine.php`, `Http/Controllers/PurchaseController.php`) use Inventory models and actions directly (28 imports) |
| Inventory reads Orders pricing and tables | `Inventory/Queries/BuildProductUnitEconomics.php` uses `OrderPricingEngine`; `Inventory/Actions/ConsumeDeliveredOrder.php` reads `orders`/`order_items` with `DB::table` |

Do not add new violations; remove these when the owning area is reworked.

## Multi-tenancy

Every business row carries a NOT NULL `restaurant_id` whose column default is the PostgreSQL session setting `app.current_restaurant_id`. `RestaurantContext` (a singleton built from `config('tenancy.default_restaurant_id')`, default `1`) applies it on every new connection. Business unique keys are scoped per restaurant. Read isolation is **not** implemented: it is planned as PostgreSQL row-level security (not Eloquent scopes) because many read models use `DB::table`. See [DATABASE.md](DATABASE.md#tenancy) and [ADR 0012](decisions/0012-tenant-ready-schema.md).

## Branding

`Core/Branding/RestaurantBranding` reads and updates only the restaurant selected by `RestaurantContext`; it has no business-module dependencies. Settings owns its administrative HTTP write surface, under the same authorization as existing general settings. `BrandingServiceProvider` lazily supplies the root view; Inertia shares validated palette values for subsequent navigation. The provider performs no database access during console boot or migrations. See [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) and [ADR 0014](decisions/0014-light-theme-restaurant-branding.md).

## Access model

- A user reaches `/admin` only through an active membership (`restaurant_user`) in the current restaurant. The membership's role is one of six code-defined roles (`owner`, `manager`, `cashier`, `waiter`, `kitchen`, `accountant`); `Identity\Enums\Role::permissions()` maps each to code-defined permissions (`Identity\Enums\Permission`), registered as Gate abilities of the same name.
- Routes use `can:<permission>`; policies and Form Requests check the same permissions. `use-pos` (`orders.manage`) and `operate-cashier` (owner, manager, cashier) remain for the internal POS order command.
- `users.is_admin` and `users.staff_profile` are kept one release for rollback and are not read. There is no runtime role editor. Details: [SECURITY.md](SECURITY.md#roles-and-permissions), [ADR 0013](decisions/0013-code-defined-roles-and-permissions.md).

## Durable decisions

| Decision | Consequence | Record |
| --- | --- | --- |
| Modular monolith on one PostgreSQL database | Cross-module consistency uses local transactions, not distributed ones | — |
| One backend pricing engine | Admin and public checkout cannot diverge on grouping or totals | [ORDERS_AND_PRICING.md](ORDERS_AND_PRICING.md) |
| Immutable order snapshots | Catalog, address, add-on or settings changes never rewrite history | [ADR 0002](decisions/0002-safe-administrative-order-editing.md) |
| PostgreSQL sequence for `TP-000001` IDs | Concurrency-safe; rollbacks may leave harmless gaps | [DATABASE.md](DATABASE.md) |
| Public slugs, internal IDs | Public checkout never exposes database IDs | [SECURITY.md](SECURITY.md) |
| Soft deletion for orders and customers | Recoverable; historical foreign keys stay intact | [ADR 0004](decisions/0004-recoverable-administrative-deletion.md) |
| Immutable ledger, derived balances | Corrections are reversals, never mutations | [ADR 0006](decisions/0006-immutable-management-ledger.md) |
| Order payment as a financial fact | `paid` is a mutable operational state; `ManagementOrderPayment` is unique per order | [ADR 0009](decisions/0009-idempotent-order-payments-in-management.md) |
| Marketing and Instagram are siblings | No cross-module automation without an explicit contract | [ADR 0005](decisions/0005-marketing-and-instagram-are-separate-domains.md) |
| Tenant-ready schema | `restaurant_id` everywhere; RLS deferred | [ADR 0012](decisions/0012-tenant-ready-schema.md) |
| Code-defined roles on a restaurant membership | Permissions change only in code; every admin route names one | [ADR 0013](decisions/0013-code-defined-roles-and-permissions.md) |

## Not implemented

Online payment gateways, WhatsApp sending (only a `wa.me` link is generated), promotions/coupons/combos, multiple or partial payments per order, automatic financial reversal on cancel or unpay, table transfer/merge, split payments, Analytics, read isolation between restaurants.
